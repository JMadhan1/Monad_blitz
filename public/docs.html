How Blind Cap works

A hidden spend limit for AI agent payments, enforced by a real zero-knowledge proof — not a policy anyone promises to follow.

Overview The mechanism Architecture Contract reference Deployed contracts Run it yourself Limitations

Overview

AI agents already pay for things autonomously on Monad — x402, agentic payment rails, MCP-driven commerce. Nothing checks whether a request is actually authorized before it settles. The obvious fix — write the spend limit on-chain — leaks a business's entire budget to every competitor watching the chain.

Blind Cap is the missing piece: an on-chain gate that checks "is this agent allowed to spend this amount?" before a payment settles — without ever revealing the agent's actual spending limit to anyone watching the chain. It's also the missing Validation Registry piece of Monad's ERC-8004 "Trustless Agents" standard — Identity and Reputation registries are live on mainnet, nothing that validates an action before it happens exists yet.

The mechanism

  1. Commit. The owner picks a limit and commits Poseidon(secretKey, maxLimit, ownerAddr) on-chain. Only the hash is written — the real number never appears on-chain, ever.
  2. Prove. Before paying, the agent generates a Groth16 zero-knowledge proof of exactly one statement: "the requested amount is ≤ the limit I committed to." The limit itself never appears in the proof or its public signals.
  3. Verify. The contract checks the proof (~250k gas, using Monad's native BN254 pairing precompiles) and marks the request Passed, or reverts.
  4. Block (the interesting part). An over-limit request can't even produce a proof — the circuit's constraint (requestedAmount ≤ maxLimit) has no satisfying witness. It's rejected before it ever reaches the chain, by math, not by a rule an admin could change.
  5. Revoke, if needed. The owner can call revokePolicy() to instantly invalidate a committed policy — e.g. after a suspected key leak. No proof can satisfy a revoked policy afterward, regardless of what secret an attacker holds.

Architecture

  • circuits/spend_auth.circom — the whole trust model in ~30 lines: a Poseidon commitment check plus a LessEqThan range comparator, compiled with Circom 2.
  • contracts/Groth16Verifier.sol — snarkjs-generated, verifies proofs on-chain via Monad's native BN254 pairing precompiles.
  • contracts/ZKSpendAuth.sol — the registry: registerPolicy, revokePolicy, validationRequest, validationResponse.
  • contracts/mocks/MockIdentityRegistry.sol — a minimal stand-in for a real ERC-8004 Identity Registry (none exists on testnet yet).
  • public/ — a static frontend, zero build step, zero backend. The ZK proof is generated in the visitor's own browser via snarkjs + the compiled .wasm/.zkey, then submitted on-chain directly through their wallet.

No server exists in this system. The "backend" is the blockchain itself — Monad Testnet/Mainnet — which the frontend talks to directly. That's a deliberate architectural choice: nothing to host, nothing that can go down, no server that could log or leak anything.

Contract reference — ZKSpendAuth.sol

registerPolicy(agentId, committedRoot)
Owner-only. Commits a policy hash for an agent. Overwrites any existing policy.
revokePolicy(agentId)
Owner-only. Instantly invalidates the committed policy — no proof can pass afterward.
validationRequest(agentId, requestedAmount)
Opens a pending validation request, returns a request hash. Reverts if no policy is committed or the policy is revoked.
validationResponse(requestHash, pA, pB, pC)
Submits the Groth16 proof for an open request. Marks it Passed on success, reverts on an invalid proof — no partial state is ever written on failure.
getValidationStatus(requestHash) / getPolicy(agentId)
Read-only views.

Run it yourself

cd Monad_blitz
npm install
npx serve public

Everything is pre-built and pre-deployed — no circuit to compile, no contract to deploy, no .env to touch. Open the printed local URL, click Launch App, connect a wallet with a little testnet MON, and go.

Honest limitations

  • Per-transaction cap, not a running budget. No cumulative spend tracking yet — an agent can spend up to the limit repeatedly.
  • One flat limit per agent. No per-recipient or time-windowed budgets yet — a Merkle-root policy would enable that.
  • Single-contributor trusted setup. Time-boxed for a one-day build. Production needs a multi-party ceremony or a setup-free system (Plonk/Halo2).
  • In-browser proving (~1–2s). Fine for a demo, too slow at high agent throughput — server-side or cached proving would fix that.
  • MockIdentityRegistry stands in for a real ERC-8004 Identity Registry, since none exists on testnet yet.
